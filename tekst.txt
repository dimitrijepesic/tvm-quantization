## 1. Apache TVM — Pregled

Apache TVM = optimization and compilation framework for DL

       model → TVM → hardware-specific native code

(today Relax instead of Relay)

       model → Relay (IR) → Tensor IR (low-level IR for kernels) → Codegen backends (x86, CUDA, ...)
                                                                       ↓
                                                                generates executable code
                                                                for target hardware

### The difference:

Relay:
- Graph of the whole ML model
- (that's why it's high level)
- Here, optimizations are:
  - op. fusion
  - constant folding
  - data layout transformation

Tensor IR:
- Lowers the Relay to look into

Another path: we can use pre-optimized op libs

## 2. AutoTVM

AutoTVM = subsystem in TVM that does automatic ML-based code optimization → ML Cost Model

1. Feature extraction — compiler creates ASTs and retrieves statistical features from it.
2. Pipeline — math expression + search space → AutoTVM → statistical cost model → prediction

AutoTVM sends the configurations it thinks are the fastest to the Code Generator.

Generator generates executable code which it sends to real target hardware. The code runs, we measure the real execution time which we store in training data.

ML model trains on that data.

The best SCM (Statistical Cost Model) is XGBoost — active learning:
- Compiler generates 10K ways to compile the convolution
- XGBoost returns the best 64
- hardware verification
- retrain XGBoost

AutoTVM here is a framework / Python package (API). AutoTVM is an interface between the system and a user that gives it an expression and a search space.

> "Bringing choice, automation and performance to ML deployment with Apache TVM and the OctoML platform" — Luis Ceze

## 4. Intro to Quantization for TVM

Quantization is converting weight values to low-bit integer without significant accuracy drop.
- Happens between Relay and deployment.

We get:
- Less storage space usage
- Faster arithmetic op
- Friendly to accelerators and ultra low-power embedded devices

### Choice spaces = set of choices I can make:
- Number of bits: 4, 8, 16
- Quantization scheme: symmetric, asymmetric
- Granularity: per-tensor, per-channel

### 3 TVM quantization phases:

1. Original — model as-is
2. After Annotate — add SimQ nodes before convolutions; everything is still float32, but rounded to int8 and converted back.
   - Here we calibrate the range for every SimQ node so the loss is minimal
3. After Realize — SimQ → Mul Clip Cast. Now we actually convert to i8 or any other format.
   - Conv. works in i32 (i8 × i8)
   - Shift Clip Cast scales the result back.

### Good to notice, in ResNet18, acc drops:
| Format | Accuracy |
|--------|----------|
| f32    | 70.8%    |
| i16    | 69.6%    |
| i8     | 69.5%    |
| i4     | 68.1%    |
| i2     | 64.1%    |

## 7. Quantization Deep Dive

float32 = decimal point number stored in 32 bits

I need a format for weights that has a wide range and fine resolution for training, but not for inference.

### Why INT8? I have three constraints:

- Hardware: I have 8-bit circuits that are fast for the multiply-accumulate op, hence INT8
- Accuracy: empirically, int8 loses <1% top-1 accuracy on ImageNet for most CNNs
- Range: int8 is enough for a typical activation distribution w/ acceptable error

### Symmetric quantization:
       real X → int q → real X:
       q = round(X / scale)
       X ≈ q · scale

       scale: if we have [-A, A]
              we want scale to be A/127
              so we map to (-127, 127]

### Asymmetric quantization: when my values are not zero-centered
       q = round(X / scale) + Z    ← zero-point offset
       X ≈ (q - Z) · scale

## 8. Convolution Math in Quantized Domain

Convolution:
       out = Σ in[i] · w[i]
           = scaled_in · scaled_w · Σ in8[i] · w8[i]

It can be scaled or scale. This (the sum) has to be in int32 since it can't fit in int8 or int16.

Hence:
       nbit_activation = 32    }  activation = accumulator
       dtype_activation = 32   }

Since I need int8 in the next layer, I need requantization:
       out = (scaled_in · scaled_w) · acc_int32
       out_int = round(out / scale_out)
               = round(((scaled_in · scaled_w) / scale_out) · acc_int32)
               = round(M · acc_int32)
                       ↓
                 real number < 1

For it to be without the floating-point math, we approximate M:
       M ≈ M_int / 2^n

       out_int = (M_int · acc_int32) >> n

- Clip = enforces the int8
- Cast = to int8

## 9. Three Quantization Phases (Detailed)

### Phase 1 — Annotate:
Fake quantization by adding SimQ ops before each conv input, after each conv output, on weights...
- Still in f32
- This has rounding errors int8 would introduce, so we measure the quantization beforehand.

### Phase 2 — Calibrate:
calibrate_mode — global scale: hardcode the same scale through the network.
       global_scale = 8:  scale = 8/127 = 0.063

This is speedy and simple because we don't need any inference. I assume all tensors fit in [-8, 8], a lazy assumption.

Alternative: max-min → scale = max(|min|, |max|) / 127

8 is an empirical guess, TVM's default value.

       global_scale = 8 but weight_scale = "power2"
         ↓
         find max abs value in weight tensor, round to nearest power of 2, /127

### Phase 3 — Realize:
We actually use int8.
       multiply → add → RS → clip → cast

       conv2d → add → RS → clip → cast → cast →
                      ↑ bias
       → mul → add → relu → add → RS → clip+cast
               ↑ rounding bias    ↑ residual/skip

## 11. Relay.build Pipeline

### relay.build:

1. Optimize = apply all enabled Relay passes from PassContext to mod. We get Relay IR.
2. Lower = Relay to TIR (Tensor IR). For each Relay operator TVM looks for schedule, a way to map ops to loops. Without autotuning we get default schedule which is not optimized for my hardware.
3. Codegen = TIR to machine code. LLVM generates x86 assembly, optimizes it and packs.

### Execution:
       graph_executor.GraphModule(libfp32["default"](dev))

- From compiled model, extract factory function for graph exec. → GraphExecutor Factory
- Call factory with device → GraphExecutor
- Wrap in GraphModule class so we are able to get benchmark

       tvm.NDArray → alloc mem on target device and copy data from numpy to TVM buffer.

## 13. Varied Bitwidth (int8 → int4 → int2 → int1)

- Native vs logical mode:
  - native: dtype="int{n}" (TVM-ovi sub-byte tipovi)
  - logical: dtype="int8" ali nbit=n (pakovano u int8 kontejner)
- Šta puca i gde — referenca na diagnostics/failure_analysis.txt (probe_int1/2/4/uint8)
- Zaključak: koje precizije su realno upotrebljive na LLVM x86

## 14. Zašto je int8 sporiji od fp32 na x86 (root cause)

- Default schedule iz TOPI-ja nije optimizovan za int8 na x86 (nedostaje VNNI/AVX512-VNNI putanja ili nije pogođena).
- Bez AutoTVM/MetaSchedule tuninga, requantizacija (mul → add → RS → clip → cast) dodaje overhead koji nije amortizovan vektorizacijom.
- Otud onih 13 koraka per layer umesto 3.

- int8 nije free lunch — treba mu (a) hw podrška za int8 MAC, (b) tunirani schedule.
- Na laptop CPU bez VNNI putanje: fp32 ostaje brži.
- Za ARM/embedded: kvantizacija ima smisla čak i bez tuninga.

## 19. Cross-compilation (detaljno)

Šta je: kompajliranje koda na jednoj mašini (host — tvoj x86 laptop) za drugu arhitekturu (target — ARM Raspberry Pi). Binary koji ispadne ne može da se pokrene na hostu, samo na targetu.

Kako se manifestuje u tvom kodu (03_cross_compile_arm.py):

1. TVM target string — kažeš LLVM-u za koju arhitekturu da generiše IR:
       target = "llvm -device=arm_cpu -mtriple=aarch64-linux-gnu -mcpu=cortex-a72"
   - mtriple=aarch64-linux-gnu → 64-bit ARM Linux
   - mcpu=cortex-a72 → konkretan CPU (Pi 4) → LLVM zna koje instrukcije (NEON, fp16, itd.) sme da koristi

2. Cross linker — TVM generiše objektne fajlove, ali za finalni .so ti treba ARM linker, ne sistemski gcc:
       cross_cc(... cc="aarch64-linux-gnu-gcc")
   To je GCC toolchain koji proizvodi ARM binarije iz x86 hosta (instalira se sa apt install gcc-aarch64-linux-gnu).

3. Artefakti (.so, .json, .params) → kopiraš ih na Pi (ili QEMU) i tamo radiš inference. Bez ovog koraka, model koji si kompajlirao za x86 ne bi mogao da se pokrene na Pi-u.

Zašto to radiš ovde: ARM ima NEON SIMD intrinsike za int8 MAC operacije. Cilj je bio da pokažeš da kvantizacija ima više smisla na embedded targetima nego na laptop x86.

## 20. AutoTVM (detaljno) — i zašto ga nisam koristio

Šta je: subsistem iz sekcije 2. Umesto da uzmeš default schedule (default raspored petlji, tile veličine, vektorizacija) za conv2d, AutoTVM:

1. Generiše hiljade kandidatskih schedule-a iz search space-a za tvoj operator (npr. različite tile veličine, redosled petlji, način vektorizacije).
2. XGBoost cost model rangira kandidate.
3. Top N se kompajluje i meri na realnom hardveru (target uređaju).
4. Stvarna vremena se vraćaju u cost model → retraining → bolja predikcija.
5. Najbolji schedule se snima u tuning.log i koristi pri sledećem relay.build.

Rezultat: schedule koji koristi tvoj konkretan CPU (cache veličine, VNNI/NEON, broj jezgara) maksimalno.

Zašto ga nisi koristio:

1. Vremenski skupo — tuning ResNet50 conv2d-a ide u redu sati po targetu. Imaš dva targeta (x86 + ARM/QEMU) i 5+ konfiguracija (fp32, int8, int4...). Ukupno bi bili dani.

2. QEMU emulacija meri besmisleno — AutoTVM bira schedule na osnovu realnih vremena na targetu. QEMU instrukcije ne odgovaraju realnom hw timingu, pa bi tuning na QEMU dao pogrešne odluke. Tuning bi imao smisla samo na realnom Pi-u.

3. Cilj projekta nije bio "kako najbrže izvršiti" — već "šta kvantizacija radi sa execution-om". Default schedule pokazuje baseline ponašanje kvantizacije; AutoTVM bi maskirao tu sliku jer bi i fp32 i int8 dobili optimizovane schedule-ove iz različitih search space-ova.

4. Bez VNNI na laptopu i tako — i sa AutoTVM-om, ako tvoj CPU nema int8 dot-product intrinsike, gornja granica za int8 ostaje skromna. AutoTVM ne menja hw mogućnosti, samo bolje koristi ono što postoji.

5. Trenutno je AutoTVM legacy — TVM ga zamenjuje MetaSchedule-om (novija generacija auto-tuninga sa boljim search space-om). Da si ulagao vreme u tuning, MetaSchedule bi bio razumniji izbor.

Šta to znači za zaključak rada: ono "int8 sporiji od fp32 na x86" je realan default-schedule rezultat — pošten benchmark bez tuning bias-a. Tuning je eksplicitno nastavak rada, ne nedostatak postojećeg.
